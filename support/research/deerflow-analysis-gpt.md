# Using DeerFlow to Replace CRUCIBLE and THE_FACTORY

DeerFlow is a “super agent harness” for long-horizon AI tasks – essentially an extensible agent runtime that includes built‑in memory, a sandboxed execution environment, parallel sub‑agents, and Markdown‑defined “skills” for workflows【46†L699-L707】【16†L711-L719】.  Its latest (2.0) rewrite is fully featured out of the box: **every task runs in an isolated Docker container with a full filesystem** (workspace, uploads, outputs)【16†L792-L800】.  It also provides a core toolset (web search, fetch, file ops, bash, etc.) and support for custom tools via plugins【16†L728-L730】.  Crucially, DeerFlow can spawn *sub-agents* on the fly so complex tasks (minutes–hours) are decomposed into parallel threads【16†L778-L787】.  Context is managed aggressively: completed sub‑tasks are summarized and offloaded so the context window stays sharp【16†L812-L821】.  Finally, DeerFlow maintains **long-term memory** across sessions (user profile, preferences, accumulated knowledge) under local control【16†L823-L831】.  (All of these capabilities are accessible via an HTTP/CLI interface or embedded Python client, and even a special `claude-to-deerflow` skill for Claude Code users【16†L749-L758】.) 

By comparison, the CRUCIBLE and THE_FACTORY projects (as described) appear to use static markdown files (like `CLAUDE.md`, `INIT.md`, etc.) and custom scripts to manage research workflows.  We could not locate public documentation for these repos, but their filenames suggest a Claude‑Code style framework: *README* plus markdown-based instructions and logs (e.g. *LEARNINGS.md*, *PROTOCOL_IMPROVEMENTS.md*, *SYNTROPY.md*).  These likely encode planning, configuration, and output logging in fixed templates.  In this light, many components of CRUCIBLE/THE_FACTORY can be **replaced by DeerFlow’s built-in features**:

- **Skills/Workflows**: DeerFlow defines “skills” in Markdown (see `skills/public/…/SKILL.md`) that specify step-by-step agent workflows【16†L711-L719】.  The existing *CLAUDE.md* and *INIT.md* instructions from CRUCIBLE/THE_FACTORY could be converted into DeerFlow skills or prompts.  For example, a “research” skill in DeerFlow already covers multi-phase analysis; any custom protocols in THE_FACTORY could similarly be expressed as new skills.  This means you wouldn’t need bespoke prompt engineering files – DeerFlow’s workflow engine handles sequences of tasks automatically.  (Skills are loaded on demand, keeping the agent’s context lean【16†L711-L719】.)

- **Tools and Integration**: If the old projects used external tools or APIs (web search, scraping, data processing), DeerFlow already integrates these. Its core tools include web search and fetch, file I/O, and bash execution【16†L728-L730】.  Any specialized functionality in CRUCIBLE (e.g. querying a custom database or API) can be added as a custom tool or Python function in DeerFlow.  Notably, DeerFlow has a **Claude Code integration** – you can run `/claude-to-deerflow` inside Claude Code to hand off work to DeerFlow【16†L749-L758】. This means existing Claude-based workflows (like those defined in *CLAUDE.md*) can transition to DeerFlow with minimal change, still using familiar slash commands to queue tasks or check status.

- **Sub‑Agents/Parallelism**: DeerFlow’s multi-agent orchestration would subsume any manual parallelization.  For example, if CRUCIBLE breaks a problem into parts via separate Claude threads or scripts, DeerFlow can spawn sub-agents automatically【16†L778-L787】.  These sub-agents have their own isolated context and tools, run in parallel, and return structured results to be merged.  In practice, a long research goal in CRUCIBLE could become a single DeerFlow task with many sub-agents exploring different angles, vastly simplifying the workflow.

- **Sandboxed Execution**: DeerFlow’s Docker-based sandbox gives each agent its own filesystem【16†L792-L800】.  Any code that THE_FACTORY runs (e.g. data pipelines, file manipulations, code generation) can now execute in a secure container.  Previously, CRUCIBLE may have needed external scripts or CLIs; with DeerFlow it just runs `bash` commands or Python within the agent (the agent “has its own computer”【16†L792-L800】).  This unifies the environment and prevents side effects between tasks.  For example, if THE_FACTORY currently relies on host-side scripts, those can be invoked inside DeerFlow’s sandbox, making the process auditable and reproducible.

- **Context Management**: DeerFlow automatically **summarizes and compresses context** as sub-tasks complete【16†L812-L821】.  If CRUCIBLE/THE_FACTORY suffered from context bloat (common in long Claude sessions), DeerFlow’s engine will offload finished parts to files and keep only essentials.  This can replace any manual summarization steps.  Over many steps, this ensures the main agent stays within model limits even as the task complexity grows.

- **Long-Term Memory**: The *LEARNINGS.md* in the old projects presumably captured insights across sessions. DeerFlow’s persistent memory can fulfill this role automatically【16†L823-L831】.  Instead of manually updating a file, DeerFlow learns your preferences and facts over time.  For example, any domain knowledge or repeated instructions you kept in LEARNINGS.md could be migrated into DeerFlow’s memory.  DeerFlow even skips duplicate facts, so memory stays clean【16†L823-L831】.  This means institutional knowledge is kept without manual file edits.

Overall, most of CRUCIBLE’s “boilerplate” (message formatting, queue management, iterative planning) and THE_FACTORY’s execution framework could be **migrated into DeerFlow’s architecture**.  In practice, one would:

- **Step 1: Install and configure DeerFlow.**  Clone the repo and run `make config` to generate local config files【49†L351-L359】.  Add any API keys or models needed (DeerFlow supports OpenAI/GPT, Claude, etc., as shown in the config examples【49†L365-L374】【49†L413-L419】).  
- **Step 2: Start DeerFlow services.**  Using Docker is recommended: `make docker-init` and `make docker-start` will pull images and run the agent and gateway processes【49†L469-L474】.  (Alternatively, one can run in local dev mode via `make dev` once dependencies are installed【49†L513-L520】.) At this point the DeerFlow HTTP/Gateway server will be running (by default on http://localhost:2026【49†L499-L503】) with a live sandbox.  
- **Step 3: Port existing workflows into DeerFlow skills.**  Convert CRUCIBLE’s *CLAUDE.md* instructions and any task pipelines into DeerFlow skills (Markdown files under `skills/custom/...`).  For example, a CRUCIBLE research pipeline becomes a DeerFlow `research/SKILL.md`.  The markdown can include the step-by-step plan and tool instructions.  This leverages DeerFlow’s built‑in skill loading【16†L711-L719】.  Any fixed prompts can be placed in CLAUDE.md or even directly passed to the agent using the `claude-to-deerflow` interface.  
- **Step 4: Migrate data and memory.**  If CRUCIBLE stored results or knowledge in text files (e.g. *LEARNINGS.md*), those notes can be seeded into DeerFlow’s memory store via the API.  DeerFlow’s memory API (or `/api/threads`) could be used to upload facts or documents, or simply have the agent read those files as initial context.  Over time DeerFlow will treat that info as part of its profile【16†L823-L831】.  
- **Step 5: Update Claude Code usage.**  In Claude Code, replace old slash commands (or add new ones) to use `/claude-to-deerflow`.  For example: `/claude-to-deerflow research Analyze topic X` would send that task to DeerFlow (using streaming responses, job status, file uploads, etc. – all supported【16†L763-L768】).  This maintains the same user interface while leveraging DeerFlow’s backend.  
- **Step 6: Test and iterate.**  Run some typical CRUCIBLE/THE_FACTORY tasks in DeerFlow.  Verify outputs, and adjust skill definitions as needed.  Compare performance: DeerFlow’s longer context and parallelism should produce richer, faster results in many cases.  

**Risks and Compatibility:**  Migrating to DeerFlow involves re-architecting the agent workflows, so there is upfront effort.  Any custom code or functions in CRUCIBLE/THE_FACTORY must be re-implemented as DeerFlow tools or scripts inside the container.  Models used (e.g. Claude vs GPT) should be configured in DeerFlow’s `config.yaml`【49†L365-L374】【49†L413-L419】.  If the old projects relied on synchronous blocking calls, note that DeerFlow’s HTTP interface is async and streaming-aware; existing logic may need adaptation.  Additionally, one should validate that any proprietary APIs or data sources (not built into DeerFlow) are still accessible and secure in the sandbox.  Finally, test that conversation history and threads align with expectations; DeerFlow manages threads differently (via its Gateway API) so thread IDs and logs may move.

**Summary:** DeerFlow already implements most features of a research agent stack – memory, sandbox, tools, planning – “batteries included”【46†L699-L707】.  By rewriting CRUCIBLE and THE_FACTORY workflows as DeerFlow skills and using its built-in orchestration, you can largely replace custom code with DeerFlow’s standardized pipeline.  This gives you a unified, maintained framework (and a large community) instead of standalone scripts.  With careful migration, DeerFlow can take over CRUCIBLE/THE_FACTORY’s roles, reduce manual effort, and add capabilities like true parallel sub-agents and persistent memory【16†L778-L787】【16†L823-L831】.
