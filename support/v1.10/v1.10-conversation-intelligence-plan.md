## What v1.10 Adds

v1.9.2 captures **outcomes** (runs, incidents, scorecards). v1.10 captures the
**process** — the reasoning, decisions, tool patterns, and failure modes that
explain why outcomes happened. It then defines how to turn that process data
into verified improvements.

Three new capabilities:
1. **Conversation Capture** — structured extraction of session traces
2. **Rubric-Based Assessment** — bias-mitigated multi-model evaluation
3. **Improvement Flywheel** — distillation → eval cases → application → verification

## Part 1: Conversation Capture

### 1.1 What to Capture

The "rich story" requires data at three levels:

| Level | What | Source | Format |
|-------|------|--------|--------|
| **Session** | Full conversation transcript | Claude Code export | Markdown |
| **Decisions** | Key decision points, alternatives considered, reasoning | Extracted from transcript | JSONL |
| **Telemetry** | Token counts, tool calls, cost, latency, model | `/cost` output + run record | JSONL |

### 1.2 Session Transcript Capture

Claude Code conversations live in `~/.claude/projects/`. To make them
analyzable:

**Post-session export hook** — After each session, export the conversation:

```
# In settings.json hooks (PostToolCall or session-end):
# Claude Code's conversation JSON is the raw material.
# Copy to project archive:
cp ~/.claude/projects/<project-hash>/conversations/<id>.json \
   .agent/conversations/<date>-<task-id>.json
```

**Alternative (manual but immediate):** At session end, use `/export` to save
the conversation as markdown. Store in `.agent/conversations/`.

**Recommended structure:**
```
.agent/conversations/
├── 2026-03-22-FE-LIVE-DECK-MONITOR.md
├── 2026-03-22-pipeline-scoring.md
└── index.jsonl   ← metadata: task_id, date, model, tokens, cost, tags
```

The `index.jsonl` links conversations to run records:
```json
{"conversation_id":"2026-03-22-FE-LIVE-DECK-MONITOR","task_id":"FE-LIVE-DECK-MONITOR","run_id":"run-2026-03-21-005","date":"2026-03-22","model":"claude-opus-4-6","tokens_in":45000,"tokens_out":12000,"cost_usd":2.15,"tags":["feature","frontend","waveform"]}
```

### 1.3 Decision Point Extraction

After capturing the transcript, a dedicated analysis agent extracts
structured decision points:

```json
{"conversation_id":"2026-03-22-FE-LIVE-DECK-MONITOR",
 "decision_id":"d-001",
 "phase":"implement",
 "type":"architectural",
 "question":"How to handle missing waveform data for tracks without analysis?",
 "alternatives_considered":["placeholder waveform","skip rendering","fallback to basic bars"],
 "chosen":"fallback to basic bars",
 "reasoning":"Maintains visual continuity without misleading accuracy",
 "outcome":"Worked — no rework needed",
 "confidence":"high"}
```

This is the "story" layer. Patterns across decisions reveal systemic issues
that run records alone cannot surface:
- Recurring architectural choices → candidates for conventions/defaults
- Low-confidence decisions that required rework → spec gaps
- Alternatives considered but rejected → design rationale (living ADRs)
- Phase where most decisions cluster → bottleneck identification

### 1.4 Pattern Categories to Extract

From the research findings, these are the high-value patterns to identify
across conversation histories:

**Process patterns:**
- Tool call sequences that correlate with success vs. rework
- Phase duration ratios (time in spec vs. implement vs. verify)
- Escalation frequency and causes
- Dead-end exploration (time spent on abandoned approaches)

**Quality patterns:**
- Types of errors caught by verification vs. escaped
- Spec ambiguities that surface during implementation
- Cross-layer changes that introduce integration issues
- Convention violations and when they're caught

**Efficiency patterns:**
- Token cost by task type and complexity
- Rework triggers (what causes a second pass?)
- Context window utilization (are sessions hitting limits?)
- Repeated research (same questions asked across sessions)

**Improvement candidates:**
- Decisions that keep recurring → candidates for defaults/conventions
- Workarounds that persist → candidates for infrastructure fixes
- Knowledge gaps that repeat → candidates for skill additions
- Manual steps that could be automated → candidates for hooks/scripts

## Part 2: Rubric-Based Assessment

### 2.1 Problems with the Current Multi-Model Critique Process

The current process (two models critique independently → cross-pollinate →
fresh agent combines → generate execution prompt) has three structural biases:

1. **Anchoring bias:** When Model B reads Model A's critique, it anchors on
   A's framing. The instruction "consider but don't take as truth" does not
   overcome cognitive anchoring — research shows 68% position preference.

2. **Sycophancy cascade:** Cross-pollination drives convergence. Models tend
   to validate points from other models rather than maintain independent
   judgment. The "agreement = significance" filter amplifies this.

3. **Uncalibrated meta-judge:** The combining agent has no rubric. It performs
   vibes-based synthesis, which is unreproducible and drifts across sessions.

### 2.2 Replacement: Independent Rubric-Grounded Assessment

**Step 1: Define the rubric BEFORE assessment.**

Each project gets a project-quality rubric with scored dimensions. These
dimensions come from the metrics framework (`.agent/metrics/README.md`) plus
project-specific concerns.

Example rubric for a project assessment:

| Dimension | Weight | 1 (Poor) | 3 (Adequate) | 5 (Excellent) |
|-----------|--------|----------|---------------|----------------|
| Architecture coherence | 3x | Layering violations, unclear boundaries | Layers defined, some leakage | Clean separation, contracts enforced |
| Code quality | 2x | No types, no tests, copy-paste patterns | Types on boundaries, partial coverage | Full types, >80% coverage, DRY |
| Error handling | 2x | Crashes on edge cases | Handles common cases | Graceful degradation, good error messages |
| API/contract discipline | 3x | Fields dropped, no validation | Validation on boundaries | Full contract testing, schema enforcement |
| Performance | 1x | Unusable latency | Acceptable for use case | Optimized hot paths, measured |
| Developer experience | 2x | Can't onboard without tribal knowledge | README + basic docs | Self-documenting, good error messages, clear patterns |
| Debt/cruft ratio | 2x | >30% dead code, stale deps | <15% debt | <5% debt, active cleanup |

**Step 2: Each model scores independently against the rubric.**

Critical: Models score BEFORE seeing any other model's output. This eliminates
anchoring bias entirely.

Prompt template for assessment agent:
```
You are assessing the quality of [PROJECT]. Score each dimension of the
rubric below on a 1-5 scale. For each score, provide:
- The score (integer 1-5)
- 2-3 specific code examples supporting your score
- One specific improvement suggestion for this dimension

Do NOT provide general impressions. Every claim must reference a specific
file, function, or pattern in the codebase.

[RUBRIC TABLE]

After scoring all dimensions, compute the weighted average.
Then list your top 3 improvement suggestions ranked by (impact × feasibility).
```

**Step 3: Synthesis agent aggregates with bias mitigation.**

The synthesis agent receives all independent scorecards and:
- Computes mean, median, and range for each dimension
- Flags dimensions with >1 point spread (disagreement = signal)
- For high-spread dimensions: quotes both models' evidence, does NOT pick a winner
- Produces a single consolidated scorecard with confidence intervals
- Ranks improvement suggestions by cross-model agreement

**Step 4: Position-swap validation for controversial dimensions.**

For any dimension where models disagree by >1 point, re-run the assessment
with the models in reversed order (if using pairwise comparison) or with
shuffled evidence presentation. Consistent disagreement after swapping =
genuine signal. Inconsistent = noise, discard.

### 2.3 Assessment Cadence

| Trigger | Scope | Output |
|---------|-------|--------|
| After 10 runs for a project | Full project assessment | Project scorecard in `.agent/assessments/` |
| After major feature completion | Feature-specific assessment | Appended to run record |
| Monthly | All active projects + pipeline | Portfolio assessment |
| On operator request | Any scope | Ad hoc scorecard |

### 2.4 Pipeline Self-Assessment

THE_FACTORY itself is assessed using the meta-scoring rubric (7 dimensions)
already defined in `.agent/evals/meta-scoring.md`. The multi-model assessment
process applies identically — independent scoring, synthesis, position-swap
for disagreements.

## Part 3: Improvement Flywheel

### 3.1 The Full Loop

```
   ┌─────────────────────────────────────────────────────────┐
   │                                                         │
   ▼                                                         │
CAPTURE ──► EXTRACT ──► ASSESS ──► DISTILL ──► APPLY ──► VERIFY
(conversations) (patterns) (rubric)  (eval cases  (code    (run evals,
                                     + prompts)   changes)  compare to
                                                            baseline)
   │                                                         │
   │              If metrics regress                         │
   └─────────────────────────────────────────────────────────┘
```

### 3.2 Distillation: Assessment → Actionable Improvements

The output of assessment (Part 2) is a scored rubric with specific
improvement suggestions. Distillation converts these into executable work:

**Step 1: Triage (human operator)**
Review the improvement suggestions. For each:
- ACCEPT → becomes a task in `.agent/tasks.jsonl`
- DEFER → stays in assessment doc, revisit next cycle
- REJECT → note reason, move on

**Step 2: Create eval cases BEFORE implementing**
For each accepted improvement, define what "improved" looks like as a
testable assertion. This is the critical step most teams skip.

Example: If assessment says "error handling is poor in bridge layer":
```markdown
# Eval: bridge-error-handling.eval.md
## Trigger: Changes to scue/bridge/
## Check: All public functions in bridge layer have try/except with
##   typed exceptions (not bare except). Error messages include
##   the operation that failed and the state at failure time.
## Pass: grep -r "except:" scue/bridge/ returns 0 bare excepts
## Fail: Any bare except, any error message without operation context
```

**Step 3: Generate implementation prompt**
With the eval case defined, the implementation prompt writes itself:

```
Task: Improve error handling in scue/bridge/ layer.

Eval case to satisfy: bridge-error-handling.eval.md
Current state: [specific examples from assessment]
Target state: [rubric level 5 description]

Constraints:
- Do not change any public API signatures
- Existing tests must continue to pass
- Follow the error handling patterns in [reference file]
```

**Step 4: Apply via standard flow**
The implementation prompt feeds into the normal feature-flow or refactor-flow.
No special process — the flows already have verification phases.

**Step 5: Verify**
After implementation:
1. Run the new eval case → must pass
2. Run the full eval suite → no regressions
3. Run `scripts/pipeline-scorecard.sh` → compare to baseline
4. In the next assessment cycle, re-score the improved dimension → must show improvement

### 3.3 What Makes This Different from the Current Process

| Current process | v1.10 flywheel |
|-----------------|----------------|
| Free-form critique | Rubric-grounded scoring |
| Models see each other's output (anchoring) | Independent scoring then synthesis |
| Agreement = significance (sycophancy risk) | Disagreement = signal worth investigating |
| One-shot execution prompt | Eval case BEFORE implementation |
| No verification that improvement stuck | Re-score in next cycle |
| Manual, unreproducible | Codified as a skill, runs consistently |

### 3.4 Connecting Conversations to Improvements Over Time

The index.jsonl in `.agent/conversations/` links conversations to run records.
Run records link to tasks. Tasks link to assessments. This chain enables:

- "Show me all conversations where rework was needed" → identify process failures
- "Show me decision points with low confidence that led to incidents" → spec gaps
- "Show me the assessment scores for SCUE over the last 3 months" → trend lines
- "Show me which improvements from last cycle actually moved the scores" → ROI on improvement effort

summary statistics: conversations per project, total cost, conversations

Adds assessment dimension scores from `.agent/assessments/` to the scorecard
output. Shows trend arrows (↑↓→) when previous assessment exists.

## Part 6: What NOT to Build

- **No custom tracing infrastructure.** Use Claude Code's conversation
  storage + manual export. Langfuse/Braintrust are for production services,
  not developer tooling pipelines.
- **No automated prompt optimization.** DSPy/MIPROv2 is for prompt search
  over metric functions. Your pipeline's "prompts" are skills and flows —
  they change structurally, not parametrically.
- **No dashboard.** Scripts + JSONL + jq. Same principle as pipeline-scoring-plan.
- **No real-time analysis.** Batch processing at session boundaries and review cadence.
- **No NLP/embedding analysis.** Decision point extraction uses LLM reading
  comprehension, not embeddings. Keep it simple.
