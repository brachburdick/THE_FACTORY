## Step 0: Archive Conversations Before 30-Day Deletion

**Goal:** Prevent loss of raw conversation data.
**Model:** N/A (deterministic script)

Claude Code auto-deletes conversation JSONL files from `~/.claude/projects/`
after 30 days. You already have 40+ extracted conversations in
`.agent/conversations/`. But any new sessions will be lost if not archived.

### Extraction behavior

The extraction script (`scripts/extract-conversations.py`) **overwrites** on
each run — it re-extracts all matching sessions and writes fresh output files.
It does NOT create duplicates. Running it twice produces the same files. This
means:
- Safe to run as often as you want
- New sessions get picked up on the next run
- If you improve the extraction format, re-running updates all files
- The index.jsonl is rewritten each run (not appended to)

### Data shape: What the extractor produces

**Merged timeline** (`.agent/conversations/timeline.jsonl`):
Interleaves events from ALL sessions chronologically, including subagent
events. This is how overlapping sessions get reconstructed into a linear story:
```jsonl

{"timestamp":"2026-03-22T14:30:15Z","session":"a1b2c3d4","project":"scue","branch":"fix/waveform","type":"assistant","thinking":[...],"tool_calls":[...]}
```

### What's captured

| Data | Included | Notes |
|------|----------|-------|
| User messages | ✅ | Truncated at 5000 chars |
| Assistant text | ✅ | Truncated at 1000 chars per block |
| Thinking blocks | ✅ (default) | Truncated at 500 chars in MD, full in JSONL |
| Tool call names + inputs | ✅ | Input summarized (file path, command, pattern) |
| Tool call results | ❌ (default) | Use `--include-tool-output` for full results (very large) |
| Subagent conversations | ✅ (default) | Inlined with timestamps for timeline merging |
| Timestamps | ✅ | ISO-8601 on every event. Enables cross-session ordering |
| Git branch | ✅ | From session metadata |
| Token counts | ❌ | Not in raw JSONL. Approximated: chars/4 |
| Cost | ❌ | Not in raw JSONL. Must be estimated |

### Steps

1. **Run extraction immediately:**
   ```bash
   cd /Users/brach/Documents/THE_FACTORY
   python3 scripts/extract-conversations.py \
     --project "-Users-brach-Documents-THE-FACTORY" \
     --format both
   ```
   Also run for project-specific hashes if sessions exist there.

2. **Set up recurring archival** (choose one):

   The v2 script handles the string-vs-list content issue, but verify with:
   ```bash
   head -20 .agent/conversations/*.md | grep -c "^.$"
   ```
   If you see many single-character lines, the coalescing fix needs work.

**Verification:** Run the extraction script, spot-check 3 markdown files.
User messages should be complete sentences, not character-per-line.

## Step 1: Extract Patterns from Existing Conversations NOW

**Goal:** Don't wait for infrastructure — you have 40+ conversations already.
Extract high-value patterns before building the full analysis skill.
**Model:** Upper-mid tier (Claude Sonnet 4.5 or Gemini 3.1 Pro)

### Why not start with infrastructure?

You already have the data. Patterns inform what the assessment rubric should
measure. Early extraction validates whether the conversation format is rich
enough (or needs improvement).

### How to analyze: parallel lens agents → synthesis

For 20 sessions, the workflow is:

```
20 sessions → group into 4 batches of 5 (by time proximity)
                    ↓
         For each batch (4 batches):
         ┌─────────────────────────────────────┐
         │  Lens A (efficiency)    ─┐          │
         │  Lens B (quality)       ─┤ parallel │
         │  Lens C (knowledge)     ─┘          │
         └─────────────────────────────────────┘
                    ↓
         12 lens reports (3 per batch)
                    ↓
         Per-batch synthesis (4 runs, upper-mid model)
                    ↓
         4 batch syntheses
                    ↓
         Final synthesis (1 run, frontier model)
                    ↓
         Ranked improvement list (project + pipeline split)
```

**Why parallel lenses instead of one big prompt?**
- Each lens has a focused evaluation rubric — no attention dilution
- Different lenses can use different model tiers (Lens A needs less code
  comprehension than Lens B)
- Parallel execution — 3 agents run simultaneously per batch
- Independent observations surface cross-cutting issues in synthesis
  (a pattern visible to both Lens A and Lens C is higher-signal)

**Why batches of 5?**
- 5 conversation markdown files fit comfortably in a single context window
- Batching by time proximity lets the lens agent see connections between
  related sessions (bug found in session 1, fix attempted in session 2)
- Cross-batch synthesis catches patterns that span time periods

### Steps

1. Select 20 sessions (richest = most messages + tool calls + subagents):
   ```bash
   python3 -c "
   import json
   with open('.agent/conversations/index.jsonl') as f:
       entries = [json.loads(l) for l in f if l.strip()]
   entries.sort(key=lambda e: e.get('end', ''), reverse=True)
   for e in entries[:20]:
       sid = e['session_id'][:12]
       msgs = e['user_messages'] + e['assistant_messages']
       tools = e['total_tool_calls']
       sa = e['subagent_count']
       print(f'{sid}  {msgs:>4} msgs  {tools:>3} tools  {sa:>2} sa')
   "
   ```

2. Group into 4 batches of 5 by time proximity.

3. For each batch, run 3 lens agents in parallel using the prompts in
   `forge/conversation-analysis/PROMPTS.md`:
   - **Lens A (Process Efficiency):** Mid-tier model (Haiku 4.5 / Gemini Flash)
   - **Lens B (Quality & Correctness):** Upper-mid model (Sonnet 4.5 / GPT-4.1)
   - **Lens C (Learning & Knowledge):** Upper-mid model (Sonnet 4.5 / Gemini Pro)

4. Per-batch synthesis: feed 3 lens reports to synthesis agent (Sonnet 4.5)

5. Final synthesis: feed 4 batch syntheses to frontier model (Opus 4.6)

6. Review the ranked improvement list. Patterns that surprise you are the
   most valuable.

**Verification:** You have a pattern report. At least 3 patterns should be
things you didn't already know from reading PROTOCOL_IMPROVEMENTS.md entries.

## Step 4: Create the Assessment Skill

**Goal:** Codify the multi-model assessment process so it's reproducible.
**Model:** Upper-mid (Sonnet 4.5) for skill authoring

1. Create `forge/project-assessment/SKILL.md` containing:
   - Trigger patterns: "assess", "critique", "quality review", "score project"
   - The assessment protocol (see v1.10 plan §2.2)
   - Prompt templates for each assessment agent
   - Output format: project assessment record (JSON)
   - Storage: `.agent/assessments/<project>/<date>.json`

2. Create `.agent/assessments/` directory structure
3. Create `.agent/schemas/project-assessment.json`
4. Add the skill to the trigger table in `CLAUDE.md`

### Assessment Protocol Summary

**Phase 1: Calibration (one-time per project)**
YOU manually score 2-3 dimensions. These become calibration anchors.

**Phase 2: Independent scoring (per model, cross-family)**
Each model scores the full rubric independently. NO model sees another's output.
- Model A: Claude Opus 4.6
- Model B: GPT-5.3 (or latest available)
- Model C: Gemini 3.1 Pro

**Phase 3: Synthesis (separate agent, Opus 4.6)**
Computes mean/median/range per dimension. Flags >1 point spread as DISAGREEMENTS.
Does NOT average away disagreements — disagreement IS the signal.

**Phase 4: Position-swap validation (for disagreements only)**
Different model (not one of the original scorers) scores using only the evidence,
not the scores. If consistent → one side wins. If inconsistent → human escalation.

**Verification:** Running the skill against one project produces a structured
assessment with per-dimension scores, evidence, and explicit disagreement flags.

## Step 5: Run Your First Rubric-Based Assessment

**Goal:** Validate the assessment process and establish baselines.
**Models:** Frontier × 3 families (see Step 4 protocol)

For each project (start with the one you care most about):

1. Your calibration (5 min): Score 2-3 dimensions roughly yourself
2. Session A (Model 1): Independent full-rubric scoring
3. Session B (Model 2): Independent full-rubric scoring
4. Session C (Model 3): Independent full-rubric scoring
5. Synthesis session: Merge scorecards, flag disagreements
6. Operator triage: ACCEPT / DEFER / REJECT each suggestion.
   **Record your triage rationale** — this trains future triage heuristics.

**Verification:** You have a scored baseline. Suggestions are triaged with
rationale recorded.

## Step 6: Create Eval Cases for Accepted Improvements

**Goal:** Define "improved" as testable assertions BEFORE implementing.
**Model:** Mid-tier (Sonnet 4.5 or Haiku 4.5)

For each accepted improvement suggestion:

1. Write an eval case in `.agent/evals/` that encodes the target state
2. The eval case must be runnable (grep, script, or LLM-as-judge with rubric)
3. Run the eval case against the current codebase → it should FAIL

**For project improvements** → eval case in the project's `.agent/evals/`
**For pipeline improvements** → eval case in root `.agent/evals/`

**Verification:** Each accepted improvement has a failing eval case.

## Step 7: Generate Implementation Prompts

**Goal:** Turn assessment findings into executable agent instructions.
**Model:** Upper-mid (Sonnet 4.5)

For each accepted improvement, write a self-contained implementation prompt:
- The specific eval case to satisfy
- Current state (from assessment evidence)
- Target state (from rubric level 5 description)
- Constraints (no API changes, existing tests must pass, etc.)
- The appropriate flow to use (feature-flow or refactor-flow)
- Whether this is a project change or a pipeline change

Store in `.agent/improvement-prompts/<task-id>.md`.

**Verification:** A prompt exists for each improvement. A fresh agent with
only the project's CLAUDE.md and this prompt could execute it.

## Step 8: Apply Improvements

**Goal:** Execute the improvements using standard flows.
**Model:** Frontier (Opus 4.6) — this is writing/modifying code

For each improvement prompt:

1. Start a new session with the implementation prompt
2. The agent follows the appropriate flow (feature-flow or refactor-flow)
3. At session end: run record, conversation export, index update
4. **Run the self-assessment prompt v2.1** — classify observations
5. Run the specific eval case → should now PASS
6. Run the full eval suite → no regressions

**Verification:** Eval cases pass. No regressions. Changes committed on branches.

---

## Step 9: Close the Loop — Re-Assess

**Goal:** Verify improvements actually improved things.
**Models:** Same as Step 5 (frontier × 3 families)

After applying improvements:

1. Re-run the rubric-based assessment (Step 5) for the same project
2. Compare dimension scores to the baseline assessment
3. For each accepted improvement:
   - Did the targeted dimension score improve? → VERIFIED
   - Did any other dimension regress? → REGRESSION — investigate
   - Is the eval case still passing? → DURABILITY
4. Update triage heuristics: Which suggestion categories moved scores?

**Verification:** You can show, with data, which improvements worked.
